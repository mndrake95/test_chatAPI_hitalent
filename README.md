
# Chat & Message API (FastAPI + SQLAlchemy Async)

Асинхронное API для управления чатами и сообщениями, разработанное в рамках тестового задания. Проект реализует полноценный цикл работы с мессенджером: создание пользователей, чатов и ведение переписки с поддержкой каскадного удаления и автоматической валидации данных. 

## 🚀 Основные возможности

* 
**Чаты и Сообщения**: Создание чатов и отправка сообщений с автоматической привязкой к автору и чату. 


* 
**Каскадное удаление**: При удалении чата все связанные сообщения удаляются на уровне БД автоматически. 


* 
**Умный GET**: Получение данных чата вместе с последними  сообщениями (по умолчанию 20, максимум 100), отсортированными по времени. 


* **Валидация данных**:
* Автоматический **тримминг пробелов** по краям для заголовков и текстов. 


* Ограничение длины: чат (1–200 символов), сообщение (1–5000 символов). 


* Защита от создания сообщений в несуществующих чатах (404 Not Found). 




* 
**Редактирование**: Возможность изменять текст уже отправленных сообщений (метод PATCH). 



## 🛠 Технологический стек

* 
**Framework**: FastAPI 


* 
**Database**: PostgreSQL (через асинхронный драйвер `asyncpg`) 


* 
**ORM**: SQLAlchemy 2.0 (Async) 


* 
**Validation**: Pydantic v2 


* 
**Testing**: Pytest + AnyIO + HTTPX 


* 
**Infrastructure**: Docker & Docker Compose 



## 📦 Запуск проекта

Для запуска всей инфраструктуры (API + PostgreSQL) вам понадобится только установленный **Docker**. 

### 1. Клонирование репозитория

```bash
git clone https://github.com/mndrake95/test_chatAPI_hitalent.git
cd test_chatAPI_hitalent
```

Создайте файл `.env` из примера:

```bash
cp .env.example .env
```

Если вы запускаете проект или тесты в Docker — создайте файл `.env.docker` вручную. В репозитории присутствует шаблон `./.env.docker.example` — скопируйте его и при необходимости отредактируйте:

```bash
cp .env.docker.example .env.docker
# или
# echo 'DB_URL=postgresql+asyncpg://postgres:postgres@db:5432/chat_db' > .env.docker
```

### 2. Запуск приложения

```bash
docker-compose up --build

```

API будет доступно по адресу: `http://localhost:8000`
Интерактивная документация Swagger: `http://localhost:8000/docs`

### 3. Запуск тестов

Проект покрыт 7 асинхронными тестами, проверяющими все сценарии — от успешного создания до ошибок валидации и каскадного удаления.

```bash
# Прогон тестов в Docker (контейнер с тестами ожидает готовности БД)
docker-compose up --abort-on-container-exit --exit-code-from tests tests
```

## Работа с БД, тестами и локальный запуск сервера 🔧

Кратко: проект использует PostgreSQL для разработки и тестов. Для локальной разработки используйте `DB_URL` в `./.env` (хост = `localhost:5433`), для запуска тестов в Docker — `./.env.docker` (хост = `db`). ✅

### Переменные окружения (файлы)

- `./.env` — для локального запуска (не коммитится, уже указан в `.gitignore`).
- `./.env.docker` — для `docker-compose` (используется сервисом `tests` через `env_file`). Этот файл не хранится в репозитории (добавлен в `.gitignore`); создайте его вручную при необходимости (пример содержимого ниже).

Примеры:

```
# .env (локально)
DB_URL=postgresql+asyncpg://postgres:postgres@localhost:5433/chat_db
```

```
# .env.docker (для docker-compose)
DB_URL=postgresql+asyncpg://postgres:postgres@db:5432/chat_db
```

### Запуск сервера локально (разработка) 🚀

1. Запустите PostgreSQL локально или поднимите DB-контейнер:
   - локально: установите и запустите Postgres на порту `5433` или
   - через Docker: `docker-compose up -d db` (поднимет контейнер БД, доступный на `localhost:5433`).
2. Запустите приложение:

```
uvicorn app.main:app --reload
```

> Убедитесь, что в `./.env` указан корректный `DB_URL` с `localhost` (иначе `uvicorn` будет падать с error `getaddrinfo failed`).

### Примечание по тестам в Docker 🧪

- Контейнер `tests` берёт переменные из `./.env.docker` и обращается к сервису БД по имени `db` внутри Docker-сети (`db:5432`).
- Для стабильности тестов в `docker-compose.yml` настроен `healthcheck` для Postgres и `depends_on` с условием `service_healthy`.

### Типичные проблемы и решения ⚠️

- `socket.gaierror / getaddrinfo failed` — указанный хост в `DB_URL` не резолвится в текущем окружении (например `db` при локальном запуске). Решение: либо запустить DB-контейнер (`docker-compose up -d db`) и использовать `localhost:5433` в `.env`, либо поправить `DB_URL` на локальный адрес.
- `Connection refused` при тестах — проверьте, что `tests` использует `env_file: .env.docker` и сервис `db` проходит `healthcheck`.

## 📝 Особенности реализации

* **Асинхронность**: Весь путь запроса — от FastAPI до базы данных — работает в асинхронном режиме.
* **ID**: Вместо стандартных `int` используются `UUID4` для повышения безопасности и распределенности системы.
* 
**Docker Healthcheck**: Контейнер с тестами дожидается полной готовности базы данных перед запуском, что исключает ошибки подключения. 

## 🛠 Трудности и решения

В процессе разработки я столкнулся с несколькими техническими вызовами, которые помогли лучше изучить работу асинхронных систем и миграций.

### 1. Асинхронность и SQLAlchemy 2.0

**Проблема:** При переходе на асинхронный движок (`asyncpg`) стандартные методы работы с ORM начали выдавать ошибки. Например, возникали проблемы с «ленивой загрузкой» (Lazy Loading) связанных сообщений при получении чата.
**Решение:** Я полностью перешел на синтаксис SQLAlchemy 2.0, используя `select` и метод `.scalars().all()`. В эндпоинте получения чата я реализовал явную загрузку сообщений в одном контексте сессии, чтобы избежать разрывов соединения.

### 2. Валидация и "мусорные" данные

**Проблема:** В ТЗ было требование по триммингу пробелов и запрету на пустые сообщения. 
**Решение:** Я использовал возможности Pydantic v2, добавив `model_config = ConfigDict(str_strip_whitespace=True)` в базовые схемы. Это позволило автоматически очищать данные на входе. Также я внедрил `min_length=1`, что в связке с триммингом дает гарантию отсутствия пустых сообщений.

### 3. Управление схемой базы данных: Автогенерация vs Миграции

**Проблема:** Использование Alembic для миграций — это стандарт индустрии, однако в условиях Docker-окружения для тестового задания это часто усложняет первый запуск проекта (требуется вручную пробрасывать команды `upgrade head`).
**Решение:** * Я сознательно выбрал использование асинхронного lifespan-контекста в FastAPI. При старте приложения срабатывает метод `conn.run_sync(Base.metadata.create_all)`, который проверяет наличие таблиц и создает их, если они отсутствуют. Это обеспечивает "нулевую конфигурацию" — проект готов к работе сразу после сборки контейнера.

### 4. Тестирование в Docker

**Проблема:** Тесты часто падали при запуске через `docker-compose`, потому что контейнер с тестами стартовал быстрее, чем база данных успевала принять первое соединение.
**Решение:** Я настроил **Healthcheck** для сервиса базы данных в `docker-compose.yml`. Теперь контейнер с тестами ожидает статус `service_healthy` от PostgreSQL, что гарантирует стабильность прохождения CI/CD цикла.
